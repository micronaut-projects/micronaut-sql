// tag::title[]
= Data Source Runtime Password Change
// end::title[]

// tag::intro[]
Micronaut SQL supports updating JDBC datasource credentials at runtime without restarting the application.

When a RefreshEvent occurs and a datasource's username or password property changes, the framework detects the change and propagates the new credentials to the underlying connection pool, then evicts existing connections so new ones are created with the updated credentials.
// end::intro[]

// tag::how-it-works[]
=== How it works

- The application observes `datasources.<name>.password` and `datasources.<name>.username` configuration keys
- On a `RefreshEvent`, every datasource whose `username` or `password` key is in the event is checked: its configured username and password are compared with the last applied ones, and the ones that changed are applied together. The new values are always read from the application configuration, the values in the event are not used, so the event should not contain secrets.
- On a `RefreshEvent` without specific keys (`new RefreshEvent()`), every configured datasource is checked the same way. Call `Environment.refresh()` before publishing such an event so the new values are loaded.
- Implementations for the supported pools set the new username and/or password on the pool and evict existing connections so subsequent connections use the updated credentials (see the notes below for details per pool).

By default, runtime credential changes are handled automatically for each datasource.

Example configuration:

[configuration]
----
datasources:
  default:
    url: jdbc:postgresql://localhost:5432/app
    driver-class-name: org.postgresql.Driver
    username: app_user
    password: ${DB_PASSWORD}
----

When `DB_PASSWORD` is rotated and your configuration refreshes, the datasource password is updated and the pool evicts existing connections so new ones authenticate with the new password.

// tag::notes[]
=== Notes

- This mechanism is event-driven. Any mechanism that results in a Micronaut RefreshEvent with changed datasources.* username/password properties will be handled.
- Username changes are supported as well; if both username and password change in the same refresh cycle, both are applied.
- How each pool applies the new credentials:
** HikariCP and Tomcat JDBC: existing connections are softly evicted, idle connections are closed immediately and connections in use are closed when they are returned to the pool.
** Oracle UCP: the pool is reconfigured with `PoolDataSource.reconfigureDataSource`.
** Unpooled: the next connection uses the new credentials.
- Only the `datasources.<name>.username` and `datasources.<name>.password` properties are observed. Credentials set through other properties, such as `data-source-properties` or `connection-properties`, are not updated at runtime.
- Credentials of disabled datasources (`datasources.<name>.enabled: false`) are not refreshed. Datasources are created at startup, so enabling or disabling a datasource requires an application restart.
- The new credentials are applied as they are, without being verified first. Update the credentials in the database, or make sure it accepts both the old and the new ones, before publishing the event. Otherwise evicted connections can not be re-established.
- If a username is changed to empty, or a username or password can not be read from the configuration, the credentials refresh ignores the whole change of that datasource and logs a warning, so it never applies a new username with an old password or the other way round. Note that Tomcat JDBC and Oracle UCP use the datasource configuration that Micronaut re-binds on a refresh event as the pool configuration, so for these pools a changed value can still reach the pool configuration directly.
- A failure to update the pool of one datasource is logged as an error and does not prevent other datasources from being updated.
- A skipped or failed change is not lost: it is applied by the next refresh event that contains a `username` or `password` key of that datasource, or by `new RefreshEvent()`. `new RefreshEvent()` does not change anything when no credentials change is pending, so it can be published periodically to retry.
- Supported pools: HikariCP, Tomcat JDBC, Oracle UCP and unpooled datasources.
// end::notes[]
